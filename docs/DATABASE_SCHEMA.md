# Database design — proposed, not a migration

All identifiers below describe the planned relational model, not implemented tables. Each entity has an immutable ID; important records store created UTC timestamp and actor, business-date where needed, and updated timestamp/version for mutable metadata. Store UTC instants; calculate Bangladesh business dates using Asia/Dhaka (Windows mapping must be tested). Use INTEGER minor units (paisa) for posted amounts, checked 64-bit arithmetic; never SQLite REAL for money. Quantities use integer base-unit ticks with an explicit per-product scale/conversion, exact integer/decimal calculations and bounded checked arithmetic. Never rely on SQLite decimal affinity as exact storage. Historical document lines snapshot names, units, prices, discounts, taxes and costs. Schema constraints cannot substitute for transaction-level checks.

## Entity catalog and keys
- `users(id, username_normalized UNIQUE, password_hash, status, created_at, ...)`; `roles`, `permissions`, `user_roles`, `role_permissions`; `login_events`, `sessions`. Security settings and audit event details must not include passwords.
- `business_profile(id, name, owner, address, phone, email, logo_ref, invoice_footer, receipt_footer, ...)`, `settings(key UNIQUE, value, version)`; version settings where historic calculations depend on them.
- `categories(id, parent_id FK, name, status)`, `units(id, name, dimension, ticks_per_base_unit, status)`, `products(id, sku UNIQUE, name, category_id FK, base_unit_id FK, min_ticks, status, ...)`, `product_barcodes(id, product_id FK, barcode UNIQUE, format)`; `unit_conversions` constrained to compatible dimensions and explicit rational factors. Uniqueness/collation and Unicode normalization need tests.
- `customers(id, code UNIQUE, name, phone, status, ...)`, `suppliers(id, code UNIQUE, name, phone, status, ...)`; opening balances are posted ledger entries, not editable balance fields.
- `sales(id, invoice_no UNIQUE, request_id UNIQUE, request_hash, customer_id FK nullable, status, occurred_at, cashier_id FK, totals, ...)`; `sale_lines(id, sale_id FK, product_id FK, quantity_ticks, unit/price/tax/discount/cost snapshots, ...)`. Walk-ins may not have an unpaid amount without an identified customer. A sale's posted lines are immutable.
- `purchases(id, purchase_no UNIQUE, request_id UNIQUE, request_hash, supplier_id FK, status, occurred_at, totals, ...)`, `purchase_lines(id, purchase_id FK, product_id FK, quantity_ticks, unit/price/tax/discount/cost snapshots, ...)`.
- `sales_returns` / `sales_return_lines` reference original sale/line, track quantity, refundable revenue/tax/discount and original cost, restock disposition and status. `purchase_returns` / `purchase_return_lines` reference original purchase/line and record stock and payable/refund effects. Returnable quantity is checked within the write transaction against the sum of earlier posted returns; a foreign key alone is insufficient.
- `payments(id, party_type, customer_id FK nullable, supplier_id FK nullable, method, amount_minor, direction, reference, occurred_at, actor_id FK, journal_id FK, ...)`, `payment_allocations(payment_id FK, invoice_id FK, amount_minor, ...)`; direction/party rules and allocation ceilings enforced in the command transaction; advances remain unallocated. Separate explicit constraints for customer vs supplier references, including opening balances/credits. Never mutate past allocations without a traceable reversal.
- `stock_balances(product_id FK PRIMARY KEY, quantity_ticks, inventory_value_minor, version)` is a transactionally maintained projection; `stock_movements(id, product_id FK, quantity_delta, previous_ticks, new_ticks, value_delta_minor, prior_value_minor, new_value_minor, type, reason, reference_type, reference_id, actor_id FK, occurred_at)` is immutable. A movement and projection update are atomic and use checked arithmetic; reject negative quantities by default. Cross-check projection to ledger.
- `expense_categories`, `expenses` with date, amount, method, description, actor, attachment reference, status; edits after posting are reversals and replacements.
- `accounts(id, code UNIQUE, name, type, status)`, `journals(id, reference_type, reference_id, idempotency_key UNIQUE, status, reversal_of FK nullable, posted_at, actor_id FK)`, `journal_lines(id, journal_id FK, account_id FK, side, amount_minor CHECK > 0)`. Post only balanced journals atomically; no finalized line updates/deletes. Unique reference rules depend on transaction type and reversal. SQLite CHECK cannot validate sums across rows; posting service plus tests/optional triggers enforce balance.
- `audit_events(id, actor_id FK nullable, action, target_type, target_id, time_utc, reason, before/after safe metadata)`, `backup_records`, `license_activation` (public signed license and verification metadata only). Activation records are not signing secrets. Attachment files need a protected data directory and backup manifest.

## Integrity & access
Foreign keys, explicit `NOT NULL`, CHECK and status constraints, unique normalized identifiers, restrictive deletes for history, indexes on FK, date+ID, invoice number, SKU/barcode, normalized search keys and party/date. Archive referenced entities; do not cascade delete posted history. Search/pagination via SQL and stable sort/keyset where appropriate; measure query plans, not arbitrary record caps. Separate database connections/transactions for writes; `BEGIN IMMEDIATE` serializes competing writers, recheck stock/returns and authorization before commit. Block direct production writes except controlled services; local admin access still limits protection.

## Remaining design work
Full column-level DDL, numeric bounds/scales, explicit indexes, triggers, journal templates, migration tooling, schema compatibility, attachment/backup format and realistic concurrent/failure testing are prerequisites for implementation. There is currently **no database or migration**.
